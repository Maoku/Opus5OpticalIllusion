## Phase 9: 操作系の破綻（最優先・全項目の検証を阻害）

### 9a. UI 遷移後に移動がロックされる ★致命

**原因（特定済み）**

`src/core/input/KeyboardMouseSource.ts:37-44` の `isTextualFocus()` が

```ts
if (tag === 'BUTTON') return true;
```

でボタンにフォーカスがあると **ゲーム側のキー入力を全て捨てる**。
一方 `src/ui/HintPanel.ts:176` はパネルを閉じるとき

```ts
else this.button.focus({ preventScroll: true });
```

でヒントボタン（`<button class="hint-open">`）へフォーカスを戻す。
結果、ヒントを一度開いて閉じると **フォーカスがボタンに残り続け、以後 WASD が永久に無視される**。
`Escape` だけは通るので「Esc を押しても直らない」状態になる。
`input.suspended` は `anyModalOpen()`（設定・一覧のみ）を見ているので、この経路とは無関係。

**修正方針**

1. `isTextualFocus()` の判定を絞る。抑止するのは
   - `INPUT` / `TEXTAREA` / `SELECT` / `contenteditable`
   - `[role="dialog"]` の子孫にフォーカスがあるとき

   の 2 条件のみとし、**単独の `BUTTON` は除外しない**。
   （HUD 上のボタンにフォーカスが残っただけで操作不能になる設計をやめる）
2. `HintPanel.#setStage('hidden')` の戻し先を、ヒントボタンではなく **canvas** にする。
   `#scene` に `tabindex="-1"` を付け `canvas.focus()`。ダイアログを閉じたら操作面へ戻る、という原則を全 UI（`SettingsMenu` / `ExhibitList`）で統一する。
3. `Space` / `Enter` がボタン活性化と `interact` の二重発火にならないよう、
   `活性化された要素が UI ボタンなら pressed に積まない` ガードを `onKeyDown` に入れる。
4. 保険として、`main.ts` の `frame()` で
   「モーダルもヒントも閉じているのに `document.activeElement` がオーバーレイ内のボタン」
   の状態を検出したら canvas へフォーカスを戻す。

**回帰テスト（tests/input.test.ts に追加）**
- ボタンにフォーカスがある状態で `KeyW` を送ると `move.y > 0` になること
- `role="dialog"` 内のボタンにフォーカスがある間は `move` が 0 のままであること

### 9b. マウス視点操作と UI 操作の競合

**現状**

- キャンバスを左クリック → `PointerLookControls.request()` でポインタロック。カーソルが消える。
- ロック解除はブラウザの `Esc` のみ。UI がキーで操作できることはどこにも書かれていない
  （エントランス案内板の 1 行 `移動 WASD ／ 視点 マウス ／ 決定 F ／ ヒント H ／ 一覧 Tab` だけ。しかも Phase 12 で撤去予定）。
- `input.suspended` は設定・一覧を開いたときだけ `look.exit()` を呼ぶ。**ヒントパネルは対象外**なので、ヒントを開いてもカーソルが戻らない。

**修正方針**

1. **常設のキーガイドを HUD に出す。** 画面下端に小さく、状況に応じて内容を差し替える。
   - 通常時: `[H] ヒント　[Tab] 展示一覧　[O] 設定　[Esc] カーソルを出す`
   - ViewSpot ロック中: `[H] ヒント　[R] タネあかし　[Esc] 視点を離れる`
   - 何かを開いている間: `[Esc] 閉じる`

   `Hud` に `setKeyHints(lines)` を追加し、`main.ts` の `frame()` から毎フレーム更新。
   `input.activeSource === 'touch'` のときは非表示（既存のプロンプト出し分けと同じ規則）。
2. **UI を開いたら必ずポインタロックを外す。**
   `anyModalOpen()` に `hintPanel.isOpen` を含める…のではなく（ヒント中も歩けるべきなので）、
   `input.suspended` とは別に `input.releasePointer()` を用意し、
   「モーダル or ヒントが開いた瞬間」に `keyboard.look.exit()` を呼ぶ。
3. **閉じたときに自動で再ロックしない。**
   ユーザーがキャンバスをクリックした時だけ戻る。HUD に `クリックで視点操作に戻る` を数秒表示。
4. ポインタロック中は `Esc` がブラウザに吸われてページに届かない環境がある（Chrome）。
   `pointerlockchange` でロックが外れた直後 1 フレームは `cancel` を無視し、
   「Esc 一回でロック解除＋ヒントも閉じる」の二重動作を防ぐ。
5. 設定メニューに「操作方法」セクションを常設（Phase 12 で撤去する案内板の受け皿）。

**工数目安**: 9a = 半日、9b = 1 日

## Phase 10: 錯視そのものが成立していない（幾何の修正）

### 10a. ペンローズの階段が繋がっていない ★

**原因（特定済み・数値検証済み）**

`src/exhibits/penroseStairs.ts:49-51`

```ts
const t = 1 - height / eye.y;
const fake = eye.clone().lerp(start, t);
```

実際の値は
- `eye`（ローカル）= `(0, 0.98, 3.0)` … 視点 y=1.6、台の上面 y=0.62
- `height` = 16 段 × RISE 0.028 = **0.448**
- `t` = 1 − 0.448/0.98 = **0.543**
- `fake` = **(−0.27, 0.448, +1.10)**

4 本目の飛びは `corners[3] = (−0.5, 0, +0.5)` から `fake` へ架かるので、
**進行方向が +Z（視点側）**。輪を閉じるには `corners[0] = (−0.5, 0, −0.5)`＝−Z 方向へ進まなければならない。
つまり最後の飛びが逆走して手前へ飛び出しており、階段の環が視覚的にも構造的にも閉じていない。

根本は **視点が低すぎる**こと。ペンローズ階段は「高い位置から見下ろす」ことが成立条件で、
`eye.y_local` が総上昇 `height` に対して十分大きくないと `fake` が視点側へ寄る。
目安は `height / eye.y ≲ 0.2`（＝`t ≳ 0.8`）。

**修正方針**

1. パラメータを成立条件に合わせて取り直す。案（`t ≈ 0.84` になる組み合わせ）:
   - `BASE_HEIGHT` 0.62 → **0.30**（模型を低い台に置いて見下ろす）
   - `RISE` 0.028 → **0.0125**（総上昇 0.20m）
   - `VIEW_DISTANCE` 3.0 → **2.2**（模型が小さくなるぶん寄る）
   - → `eye.y_local` = 1.30、`height` = 0.20、`t` = 0.846、`fake` ≈ (−0.42, 0.20, −0.04)
     … `corners[3](z=+0.5)` → `fake(z=−0.04)` で **−Z 方向へ正しく進む**
2. 成立条件を **コードで保証する**。`build()` に不変条件チェックを入れる:
   - `fake` が視点 → `corners[0]` のレイ上にあること（投影一致）
   - `(fake − corners[3])` を XZ に落としたベクトルと `(corners[0] − corners[3])` の内積が正
     （＝最後の飛びが輪を閉じる向きに進む）

   満たさない場合は `RISE` を自動で縮めて再計算する `fitRise()` を用意し、
   将来レイアウトを動かしても壊れないようにする。
3. 中庭（`well`）の高さ・`plinth` の寸法を新パラメータに追随させる。
4. 見下ろし角が浅いと段の重なりが読めないので、`fov` 34 → 30 程度で再調整。
5. **決定事項 C**: 上記の寸法変更で不変条件テストが通らなかった場合に限り、
   見下ろし専用の ViewSpot（模型を見下ろす台の上・目線 2.4m 相当）へ切り替える。
   最初からその手を使わないのは、他展示と同じ「床に立って見る」文法を保ちたいため。

**回帰テスト（tests/exhibits.test.ts）**
- `fake` の視点投影が `corners[0]` と一致（誤差 1e-3）
- 最後の飛びの進行方向の内積 > 0
- 16 段すべてで `y` が単調増加

### 10b. ペンローズの三角形の視点位置が階段に埋まっている ★

**原因（特定済み・数値検証済み）**

| 展示 | position | standAt | フットプリント |
|---|---|---|---|
| ペンローズの階段 | (−5, −2.4) | (−5, +0.6) | 台座 1.7m 角 → x∈[−5.85, −4.15], z∈[−3.25, −1.55] |
| ペンローズの三角形 | (−5, −9.0) | **(−5, −2.8)** | — |

三角形の `standAt (−5, −2.8)` が **階段の台座の内部**（z∈[−3.25,−1.55]）。
`pedestal({ viewDistance: 6.2, dirY: 0 })` が z = −9 + 6.2 = −2.8 を返しているだけで、
他展示との干渉は誰もチェックしていない。

**修正方針**

1. Room B（x∈[−10,10], z∈[−13,3]）の配置を組み直す。案:
   - ペンローズの三角形: position (−6, −9.5) / viewDistance 6.2 → standAt (−6, −3.3)
   - ペンローズの階段: position (**+5**, −3.0) / 立つ側 dirY 0 → standAt (+5, −0.8)
   - 両者を左右に振り分け、視線が互いを横切らないようにする
   - Room B の他展示（ネッカーキューブ・不可能な三又など）と合わせて一度に検証する
2. **再発防止が本題。** `ExhibitDefinition` に `footprint`（半径 or AABB）を追加し、
   全展示ぶんを走査するテストを置く:
   - 各 ViewSpot の `standAt` が、自展示以外のフットプリントに入らない
   - `standAt` が壁コライダーと重ならない（`Collision` を使って判定）
   - `standAt` が所属エリアの矩形に 0.6m マージンで収まる

   これは今回の 10b・11d（椅子の壁抜け）の両方に効く。

**工数目安**: 10a = 1 日（数値調整の試行を含む）、10b = 半日 + テスト基盤 半日

## Phase 11: 種明かしの見せ方

### 11a. チェッカーシャドウを俯瞰で比較できるようにする

**現状**: `reveal: 'strip'` は帯をフェードインするだけで、カメラは水平のまま（`fov 42` / 距離 3.1m）。
`ExhibitManager.#applyCameraReveal()` はカメラを動かす種別を `'orbit' | 'topDown'` に限定しており、
`'strip'` はカメラに触らない。

**修正方針**

1. `reveal` を **「見た目の演出」と「カメラ演出」の 2 軸**に分ける。
   `ExhibitDefinition.reveal: 'strip'` はそのまま、`revealCamera?: 'orbit' | 'topDown' | 'tilt'` を追加。
   `#applyCameraReveal()` は `revealCamera` を見るようにし、既存展示は `reveal` から自動で埋める。
2. チェッカーシャドウに `revealCamera: 'tilt'` を指定。真上ではなく **見下ろし 55〜60°**
   （真上だと影の帯と円柱の関係が読めなくなる）。板全体と A/B・帯が同一画面に収まる高さへ。
3. 種明かし中は円柱を半透明に落とし、帯の全長が板の上を走るのが見えるようにする。

**校正への影響**: タイルは `MeshStandardMaterial(roughness: 1, metalness: 0)` の完全拡散で、
スポットは `decay: 0`。**輝度は視線方向に依存しない**ので、視点を変えても
`CALIBRATION = 0.185` の A/B 一致は崩れない。ただし QA チェックリストには
「俯瞰視点でも A と B のピクセル値が 1 階調以内」を追加する。

### 11b. エイムズの部屋で人形が同じ大きさだと分かるようにする

**現状**: `reveal: 'topDown'` で天井・壁を透過させて真上から台形を見せるだけ。
人形は床の四辺形上の (0.14, 0.86) と (0.86, 0.86) に固定で、俯瞰では **奥行き差＝距離差** に見えてしまい、
「同じ大きさ」の証明になっていない。

**修正方針（ポンゾと同じ手を使う）**

1. 種明かしの進行に合わせて、**左の人形を右の人形の隣へ運ぶ**。
   俯瞰視点のまま 2 体が並べば、同一寸法であることが一目で分かる。
   `setRevealed(_, progress)` で `left.position` を `onFloor(0.14, 0.86)` → `onFloor(0.66, 0.86)` へ lerp。
2. 移動の軌跡に薄いゴーストを残す（元の位置を示す半透明の同形状）。
   「動かしただけで縮んでいない」ことを担保する。
3. 補助として、2 体の頭上に **同一ジオメトリ・同一スケール**の高さバーを立てる。
   `dollHeight` から生成した 1 つの `BufferGeometry` を共有し、コード上も同一性が保証される形にする。
4. 俯瞰の高さ・画角を、並んだ 2 体と台形の床が同時に収まるよう再調整。

### 11c. ポンゾの錯視で棒をぴったり並べる

**現状**: `src/exhibits/ponzoCorridor.ts:136`

```ts
const target = nearBase.clone().add(new THREE.Vector3(0, 0.34, 0));
```

奥の棒を手前の棒の **0.34m 上** に持ってくる。視距離 2.6m で 0.34m は視野内でかなり空き、
両端の位置ずれも相まって「ぴったり同じ長さ」に見えない。

**修正方針**

1. 縦の間隔を **0.34 → 0.07** に詰める（棒の太さ 0.05 の 1.5 倍程度）。
2. 中心合わせではなく **左端合わせ** にする（長さ比較は端を揃えるほうが確実）。
   `target.x` を `nearBase.x + (nearLength − nearLength)/2` ではなく、左端が一致する位置へ。
3. 両端に細い縦のガイド線（0.006m 幅の細板）を 2 本立て、
   2 本の棒の端がどちらもガイドに接することを見せる。
4. 種明かし中は少し寄る（`revealCamera: 'tilt'` を使って距離 2.6 → 1.8、fov 55 → 42）。
5. `scale` は既に `nearDistance / farDistance` で戻しており、物理長が一致する。ここは変更不要。

### 11d. ブーシェの椅子：カメラの壁抜けと「人の大きさ変化」の弱さ ★

**原因（特定済み・数値検証済み）**

`ExhibitManager.#applyCameraReveal()` の orbit は、正解視点から **常に +72°** 回り込む。
椅子の場合:
- `centre` = position(31, 0, −3.0) + revealFocus(0, 0.6, −3.2) = **(31, 0.6, −6.2)**
- `spot.eye` = (31, 1.6, +0.4) → `radius` = 6.67、`base` = 0
- +72° の視点 = **(37.3, …, −4.1)**

Room C は x∈[14, 34]。**x = 37.3 は壁の外**。だから種明かしが見えない。

**修正方針**

1. **汎用の壁抜け防止を `#applyCameraReveal()` に入れる（本命）。**
   - `areaAt(centre)` で現在エリアの矩形を取り、視点候補を内側 0.6m マージンでクランプ
   - 角度候補を `[+72, −72, +52, −52, +36, −36]` の順に試し、
     「エリア内に収まり、かつ他展示のフットプリントに入らない」最初の候補を採用
   - どれも不可なら半径を 0.7 倍して再試行（2 回まで）

   これでペンローズの三角形・階段・ホロウマスクの orbit も同時に安全になる。
2. 椅子側は `-72°`（x ≈ 24.7）だとポンゾの廊下（x∈[22.7, 25.3]）に刺さるので、
   上記のフットプリント判定に引っかかって自動的に `+52°` などへ落ちる。
   期待どおりに落ちることをテストで固定する。
3. **人の大きさ変化を読ませる。** 現状は人形が椅子から 1.15m 横に離れた位置に立っており、
   椅子との比較になっていない。
   - 人形を **奥の椅子のすぐ脇（脚元）** へ移動し、正解視点で「椅子に座れそうな人」に見える構図にする
   - 種明かしの進行で、手前の座面が持ち上がる（既存）と同時に、
     **人形の身長 1.7m を示す目盛り**と、椅子の実寸（背もたれ高 = 0.52 × 1.9 ≈ 1.0m）を並べて出す
   - 「椅子が巨大」なのか「人が小さい」のかが切り替わる瞬間を見せるのが目的

**工数目安**: 11a = 半日、11b = 1 日、11c = 半日、11d = 1 日（うち汎用クランプ 半日）

### 11e. くぼんだ顔の鼻に影が乗る

**原因（仮説・要実測）**

`src/exhibits/hollowMask.ts:99` で `mask.castShadow = true`。
凹面のレリーフ（薄い単一サーフェス・`DoubleSide` + `alphaTest`）が自分自身にシャドウマップを投げており、
鼻の谷の縁がハードな落ち影として出ていると見られる。凸面の顔なら生じない位置に影が乗るため、
「上から照らされた凸の顔」という読みが崩れる。

**修正方針（上から順に試す）**

1. `mask.castShadow = false`。マスクは他の何にも影を落とす必要がない（台座のみ影を受ける）。
   これで自己遮蔽由来の落ち影が消え、陰影は法線由来のシェーディングだけになる。
2. 消えない場合は `Lighting` のスポット影パラメータ（`bias −0.0008` / `normalBias 0.02`）を
   この展示専用に上書きできるようにし、`normalBias` を 0.05〜0.08 へ。
3. それでも残る場合は光源の仰角を上げる（現在 origin + (0.15, 2.2, 1.6) → (0.1, 2.6, 1.0)）。
   ただし **単一方向照明は成立条件**なので、光源を増やす方向の対処はしない。
4. 併せて `alphaMap + alphaTest` で影を落とすときに矩形の影が出ていないかも確認する。

**検証**: 種明かし前に「凸の顔が上から照らされている」ように見えること、
種明かしで真横へ振ったときに凹面だと分かること。スクリーンショットで前後比較。

**工数目安**: 半日（実測込み）

## Phase 12: 情報設計と導線

### 12a. 3D 空間の立て看板を廃し、説明をヒントへ集約

**現状の在庫**

| 種類 | 生成元 | 内容 |
|---|---|---|
| エントランスの自立案内板 | `Signage` (2.0×1.2m + ポスト) | タイトル / 導入文 / 操作説明 |
| 扉上の部屋名サイン ×4 | `Signage` (2.0×0.36m) | 部屋名のみ |
| 展示ごとのキャプション板 | `ExhibitManager.#createPlate()` + `#plateposts` | 展示名 / キャプション / 注意書き |

**修正方針**

1. **自立式の案内板とキャプション板（＋支柱）を撤去する。**
   `Signage` の 1 件目と `ExhibitManager.#createPlate()` / `#plateposts` を削除。
2. 失われる情報の受け皿:
   - 展示名・キャプション → **ヒントパネルの第 0 段階**に表示（`HintContent.title` / `caption` は既にある）。
     注視中は HUD に展示名だけを小さく出し、`[H]` でヒントを開くと全文が読める形にする。
   - 「スクリーンショットでは伝わりません」等の `notice` → ヒント内に移設
   - 操作説明 → Phase 9b の常設キーガイド ＋ 設定メニューの「操作方法」
   - 入館時の導入文 → ローディング／入場画面（`LoadingScreen`）の 1 画面として提示
3. **扉上の部屋名サインは残す**（決定事項 A）。
   これは説明ではなくナビゲーションであり、撤去すると順路が読めなくなる。
   `Signage` の 2〜5 件目（`sign` サイズの 4 枚）はそのまま。Opus 棟の扉が無くなっても
   南口のサイン（z = −12.72）は開口の上に残るので、部屋の入口であることは読める。
4. 副作用: 3D テキストの焼き込み（`TextPlate` / フォントサブセット）の利用が
   部屋名サインだけになる。`tools/subsetFont.ts` の必要文字数が激減するので、
   サブセット定義を見直してバンドルを削る。
5. `tests/i18n.test.ts` の「言語切替でワールド内テキストが作り直される」系のテストを更新。

### 12b. Opus 棟の扉を削除し、最初から入れるようにする（決定事項 B）

**現状**: `main.ts:175-185`。Room A〜C の ViewSpot を 6 つ踏むと `museum.unlockOpus()`。
`DOORWAYS` の `locked: true` な扉が塞いでおり、`ExhibitList.isAvailable` も
`room !== 'opus' || museum.opusUnlocked` で一覧からのワープを禁止している。

**修正方針 — 扉という概念ごと消す。順路の提示も行わない。**

1. `layout.ts` の該当 `DOORWAYS` エントリから `locked: true` を外す。
   `wallGeometry.buildDoorPieces()` は `if (!d.locked) continue;` なので、
   これだけで **扉のメッシュもコライダーも生成されなくなり、壁の刳り抜き（開口）だけが残る**。
   他の 7 箇所の出入口と完全に同じ扱いになる。
2. `Doorway.locked` フィールドと `buildDoorPieces()`、`BuiltMuseum.doors`、
   `RoomBuilder.unlock()`、`DOOR_COLLIDER_TAG`、`#doorMaterial()` を削除。
   扉が 1 枚も無くなるため、これらは全て到達不能コードになる。
3. `Museum.opusUnlocked` / `unlockOpus()` を削除。
4. `main.ts` の `OPUS_UNLOCK_COUNT` / `viewedExhibits` /
   `viewpoint.events.on('locked', …)` の開錠ハンドラと開錠トーストを削除。
5. `ExhibitList` の `isAvailable` オプションごと削除（唯一の利用者が開錠判定だった）。
   一覧からは最初から全展示へワープできる。
6. 順路の誘導は **行わない**。扉上の部屋名サイン（決定事項 A で存置）と
   展示一覧の `order` 順があれば十分で、それ以上の順路提示は入れない。
7. `Docs/ROOM_D_OPUS_WING.md` §4（開錠条件）を「開錠制は廃止。Opus 棟は初回から開放」と改訂。
   `Docs/IMPLEMENTATION_PLAN.md` の Phase 6c の記述にも同じ注記を入れる。
8. `tests/world.test.ts` の施錠前提のテスト（扉コライダーの存在確認など）を、
   **「Room B から Room D まで壁に遮られず到達できる」検証**に置き換える。

### 12c. Opus 棟の照明を上げる

**現状**: `Lighting.PROFILES.opus = { hemi: 0.08, ambient: 0.06, key: 0.35, elevation: 75 }`。
壁 `0x24252c` / 床 `0x14151a`。極端に暗く、歩行時の視認性が低い。

**修正方針**

1. `roomD` を **明るい本体 + 暗いアルコーブ**の 2 エリアに分割する。
   `AREAS` は矩形エリアから壁を自動生成し `DOORWAYS` で刳り抜く設計なので、
   サブエリアを 1 つ足すだけで内壁付きの小部屋が作れる。
   - 新パレット `opusBright`: `{ floor: 0x24262d, wall: 0x3a3c46, ceiling: 0x1c1e24, baseboard: 0x2a2c33 }`
   - 新プロファイル `opusBright`: `{ hemi: 0.24, ambient: 0.18, key: 0.85, elevation: 72 }`
   - `roomD` 本体を `opusBright` に変更
   - アルコーブ（`roomD_alcove`、例: x∈[−13,−1], z∈[−28,−20]）は `opus` パレット／プロファイルのまま
2. **暗さが成立条件の展示をアルコーブへ集約する。**
   確定しているのは D6「縞の下の嘘」（`underTheStripes`、現在 position (−7, 0, −24)）。
   実光源のゴボ投影による同化が要なので、環境光を上げると効果が落ちる。
   → アルコーブ内にそのまま収まる位置なので移設コストは小さい。
   他の D 展示（D1/D2/D4）については `brightnessCritical` フラグと ROOM_D_OPUS_WING.md を突き合わせ、
   該当するものを同じアルコーブか第 2 アルコーブへ移す。
3. アルコーブの入口に「この先は暗い部屋です」の一言（ヒント／サイン）を添え、
   明順応の落差を予告する。
4. 明度系錯視の校正値（チェッカーシャドウの `CALIBRATION`）は Room A なので影響なし。
   ただし Opus 棟内で明度比較を行う展示があれば **再校正が必須**。

**工数目安**: 12a = 1 日、12b = 半日、12c = 1 日

## Phase 13: 美術館としての内装

**方針**: 近代美術館の装い。ただし **展示の妨げにならないこと**が絶対条件。

### 守るべき制約（これを破ると錯視が壊れる）

1. **ライトを増やさない。** `Lighting` はプール本数を起動時に固定している（実行中に本数を変えると
   three がシェーダを再コンパイルしてカクつく）。内装はすべて `emissive` かテクスチャで表現する。
2. **明度系錯視の背景を変えない。** `gallery` パレットの壁は「白すぎない中間明度」が意図的な選択。
   チェッカーシャドウ・ホロウマスク（`brightnessCritical: true`）の周囲の壁面明度は据え置く。
   変更する場合は `CALIBRATION` の再測定を必須にする。
3. **ドローコールは部屋あたり +2 まで。** `RoomBuilder` は壁・幅木をエリアごとに 1 メッシュへ
   マージしている。この方針を崩さない。

### 追加する意匠

1. **天井のスリット照明**（最も効く）
   天井に細い発光帯を並べる。`MeshBasicMaterial` の emissive のみで、実際の照明は増やさない。
   エリアごとに 1 メッシュへマージ。近代美術館の記号として最も安価で効果が高い。
2. **ピクチャーレール／上部リセス**
   壁の上端（高さ 2.6m 付近）に見切りの帯を 1 本。幅木と同じ `buildWallPieces` の仕組みで作れる。
   壁面の巨大な無地を分割し、スケール感を与える。
3. **床の目地**
   床テクスチャに 1.2m グリッドの薄い目地を焼く。現在の `#floorMaterial` は
   まだら＋ノイズのみなので、線を 1 種足すだけ。展示の真下でも主張しない濃度に抑える。
4. **エントランスの造作**
   `entrance` は天井高 6.0m を確保済み。受付カウンター相当の低いボリューム 1 つと、
   吹き抜けを活かした縦長のサイン面（部屋名サインの意匠と統一）。
5. **パレットの微調整**
   `hall` / `corridor` をわずかに冷たいオフホワイトへ。`gallery` は据え置き（制約 2）。

### 進め方

- 5 項目を一度に入れず、**1 → 2 → 3 → 4 → 5 の順に 1 つずつ入れて毎回スクリーンショット比較**。
- 各ステップで `DevHud` のフレーム時間とドローコールを記録し、モバイル想定の `low` プリセットでも
  Phase 8c で確保した性能を割らないことを確認する。

**工数目安**: 2 日
